# deploy/gke — GPU workloads on GKE (T3)

**What it does:** runs the lab's GPU checks on the cluster from `../gcp/terraform` (or any GKE
cluster with L4 nodes): a smoke test that captures how a pod sees its GPU, a CUDA sample, nccl-tests
across two L4s, GPU time-sharing, a MIG slice, and DCGM alert rules for Google Managed Prometheus.

**Cost:** each Job brings up a Spot GPU node from zero and releases it when the pod finishes (the
cluster autoscaler removes an unneeded node after about ten minutes — verify for your version).
An L4 Spot node for 15 minutes is cents; the 2 x L4 node for nccl-tests about twice that (verify
current Spot prices). Nothing here runs indefinitely except `04-time-sharing.yaml` — delete it.

**Cleanup:** `./run.sh clean` (deletes the `gpu-lab` namespace), then `terraform destroy` in
`../gcp/terraform`.

| Manifest | Pool it lands on | What to look at |
|---|---|---|
| `00-namespace.yaml` | — | everything lives in `gpu-lab` |
| `01-gpu-smoke.yaml` | `l4` (g2-standard-4; selects `gpu-lab/pool: l4`) | `probe.sh` output: `/dev/nvidia*`, the `/usr/local/nvidia` driver mount, versions → `python -m gpurt.container --log out/gpu-smoke.log` |
| `02-cuda-vectoradd.yaml` | `l4` | "Test PASSED": image CUDA runtime + node driver agree |
| `03-nccl-tests-2gpu.yaml` | `l4x2` (g2-standard-24) | `nvidia-smi topo -m`, NCCL's transport (`NCCL_DEBUG=INFO`), busbw → `python -m gpurt.nccltests out/nccl-tests-2gpu.log` (nccl-tests pinned to v2.20.0) |
| `04-time-sharing.yaml` | `l4-shared` | two pods, one GPU UUID. Scale to 3: the third does not fit the node's 2 advertised GPUs, so the autoscaler adds a second node (the pool scales 0→`gpu_max_nodes` = 2). To see a pod *stay* Pending, scale past 2 × `gpu_max_nodes` or set `gpu_max_nodes = 1` |
| `05-mig.yaml` | `a100-mig` | `nvidia-smi -L` lists a `MIG 1g.5gb Device` |
| `06-dcgm-alert-rules.yaml` | — (cluster-scoped) | GMP `ClusterRules` generated by `gpurt.dcgm.rules_manifest()`; do not edit by hand |
| `alertmanager/alertmanager.example.yaml` | — | where firing alerts go: routes for GMP's managed Alertmanager (not a Kubernetes manifest, so it sits in its own folder, out of reach of `kubectl apply -f deploy/gke/`) |

```bash
$(terraform -chdir=../gcp/terraform output -raw get_credentials)
./run.sh status        # nodes, accelerator/sharing labels, allocatable nvidia.com/gpu
./run.sh smoke         # -> out/gpu-smoke.log
./run.sh vectoradd
./run.sh nccl          # -> out/nccl-tests-2gpu.log (first run: node scale-up + image pull, 10+ minutes)
./run.sh timeshare     # needs enable_time_sharing_pool = true
./run.sh mig           # needs enable_mig_pool = true and A100 quota
./run.sh rules         # DCGM alert rules (ClusterRules), then give Alertmanager receivers (below)
DRY_RUN=1 ./run.sh nccl   # print the kubectl commands only
```

A Job that fails stops `run.sh` at once (it polls for *Complete* or *Failed*) and still saves its log.

Every GPU pod requests `nvidia.com/gpu` in `limits` (extended resources cannot be overcommitted,
so requests equal limits), selects an accelerator with `cloud.google.com/gke-accelerator`, and
tolerates the `nvidia.com/gpu` taint. How the device plugin turns that request into device nodes
and a driver mount is primer §6; how the scheduler places it is layer 03
([`03-kubernetes-gpu/gpu-scheduling`](../../../../../03-kubernetes-gpu/gpu-scheduling)).

## DCGM metrics and alerts

With `enable_dcgm = true` GKE runs a DCGM exporter and Managed Prometheus scrapes it; in *Metrics
explorer* switch to PromQL and try `DCGM_FI_PROF_SM_ACTIVE` against `DCGM_FI_DEV_GPU_UTIL` while
`./run.sh nccl` runs. Notebook 06 explains what each field means and why `GPU_UTIL` alone misleads.

**Which rules can fire depends on the exported fields** (`gpurt.dcgm.EXPORTED_BY`, read from the
upstream files on 2026-09-26 — verify for your versions):

| Exporter | Missing fields | Rules that can never fire |
|---|---|---|
| stock dcgm-exporter (`default-counters.csv`) | `DCGM_FI_DEV_CLOCKS_EVENT_REASONS`; `DCGM_FI_PROF_SM_ACTIVE`, `SM_OCCUPANCY` commented out | `GpuThermalThrottling`, `GpuHardwareSlowdown`, `GpuBusyButUnderfilled` |
| GKE-managed DCGM (field list: verify; Google's GMP DCGM example lists no XID, row-remap, clock-event or DRAM fields) | likely the health fields | likely every `GpuXid*`, row-remap and clock rule |
| self-managed exporter with [`../any-gpu/dcgm-counters.csv`](../any-gpu/dcgm-counters.csv) | none | none |

`python -c "from gpurt import dcgm; print(dcgm.rules_that_cannot_fire(open('fields.txt').read().split()))"`
answers it for any field list. For the health rules on GKE, run a self-managed exporter with the lab's
counters CSV — e.g. Google's `prometheus-engine` `examples/nvidia-dcgm` DaemonSet (namespace
`gmp-public`, scraped by a `PodMonitoring`) with its `counters.csv` ConfigMap replaced by
`../any-gpu/dcgm-counters.csv` — and disable the managed package to avoid duplicate series (verify).

**Why `ClusterRules`:** on GMP a namespaced `Rules` object evaluates only metrics from its own
namespace, and the exporter runs in a system namespace (or `gmp-public`), never in `gpu-lab`. The
cluster-scoped `ClusterRules` sees the whole cluster. Because the scraper's own target labels
(`namespace`, `pod`) win, the exporter's workload labels arrive as `exported_namespace`/`exported_pod`
(verify), which is what the rules select on.

**Where alerts go:** rules only evaluate. GMP's rule-evaluator sends firing alerts to an Alertmanager —
the managed one reads its configuration from a Secret in `gmp-public` (verify the name/key) — not to
Cloud Monitoring alerting policies. Edit the receivers in `alertmanager/alertmanager.example.yaml`, then:

```bash
kubectl -n gmp-public create secret generic alertmanager \
  --from-file=alertmanager.yaml=alertmanager/alertmanager.example.yaml --dry-run=client -o yaml | kubectl apply -f -
```

The alternative is Cloud Monitoring alerting policies with a PromQL condition (Terraform
`google_monitoring_alert_policy`, `conditions.condition_prometheus_query_language.query` in provider
8.4.0), using the same expressions from `06-dcgm-alert-rules.yaml`.

Items marked `VERIFY:` in the manifests (image tags, GKE node-label values, MIG profiles) are product
details to re-check against current documentation before relying on them.
