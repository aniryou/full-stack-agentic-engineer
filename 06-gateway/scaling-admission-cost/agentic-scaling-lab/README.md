# agentic-scaling-lab

The core concepts of scaling an agentic solution — as a primer, a Google Cloud reference architecture, and
about 650 lines of runnable Python (950 with docstrings) and four practice notebooks. Worked on one anchor scenario: a telco support agent at 100,000
conversations a day on Cloud Run and Gemini.

Nothing here needs cloud credentials; simulations run 50× faster than real time.

## What is in the box

| Path | What it is |
|---|---|
| `docs/01-scaling-primer.md` | **The primer**: why agents scale differently, the dimensions of scale, the arithmetic, the mechanisms, the failure catalogue, the growth path, how to walk the design in a review. |
| `docs/02-reference-architecture.md` | **The Cloud Run + Gemini reference architecture**: components, a turn end to end, settings per component, failure handling, alternatives. |
| `docs/03-capacity-plan.md` | The numbers, generated by `python -m scalelab.capacity`. |
| `docs/04-gcp-mapping.md` | Each core concept → the Google Cloud service that implements it → the one setting that matters. |
| `scalelab/` | **The core concepts in code** — one module per idea, each readable in five minutes. |
| `notebooks/` | **Four worked-example notebooks with fill-in-the-blank exercises**; solutions in `notebooks/solutions/`. |
| `tests/` | One test per concept (`pytest -q`, ~4 s). |

## The core concepts (`scalelab/`)

| Module | Lines | The idea |
|---|---:|---|
| `capacity.py` | ~190 | conversations → turns → calls → tokens/min; Little's law; Provisioned Throughput units and break-even; cost per conversation; what breaks first |
| `resilience.py` | ~130 | token bucket (smooth your own traffic), backoff with full jitter, circuit breaker, `call_with_retries` bounded by a deadline |
| `admission.py` | ~90 | degrade levels 0–3 from in-flight turns / 429 ratio / queue age, an in-flight cap, shedding with `Retry-After`, hysteresis |
| `loop.py` | ~140 | the turn: budgets on four dimensions, a checkpoint per step, idempotent writes, resume after a crash |
| `model.py` | ~140 | a fake Gemini with realistic latency, a shared tokens-per-minute pool that answers 429, prefix caching — and the 30-line real call |
| `tools.py` | ~70 | simulated CRM / billing systems with QPS ceilings and structured errors |
| `sim.py` | ~130 | a load generator: many users, one pool, one admission controller; latency, shedding and cost per regime |
| `clock.py` | ~30 | the virtual clock |

## Quick start

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
python -m scalelab.capacity        # the capacity plan
pytest -q                          # 13 tests, ~4 s
jupyter lab notebooks/             # start with 01_scaling_math.ipynb
```

## The notebooks

| # | Notebook | You will be able to |
|---|---|---|
| 01 | Scaling math | go from conversations/day to tokens/min, in-flight turns, GSUs and dollars in two minutes |
| 02 | The turn: budgets, checkpoints, idempotency | make a crash mid-turn produce one ticket, not two; know what to ack and what to nack |
| 03 | Rate limits, retries, breakers, admission | explain a 429, smooth traffic, jitter retries, break circuits, degrade before shedding |
| 04 | From a load test to Cloud Run settings | show the overload feedback loop and derive concurrency, instances and the in-flight cap from measurements |

Each notebook opens with the one-minute version, works the example against the code with charts, then hands you four
fill-in-the-blank exercises with checks. Practice notebooks run end to end untouched (checks print "not attempted
yet"); solutions run with every check passing.

## The anchor numbers (verify before quoting — prices and model ids move)

100 k conversations/day → 15 model calls/s average, 46 at peak, 153 in an incident → 4.6 / 13.75 / 45.8 M input
tokens per minute against a 10 M TPM Flash tier baseline → 42 / 125 / 417 turns in flight → $0.068 per conversation
with routing and caching ($0.14 without) → 69 GSUs of Provisioned Throughput for the base load, break-even at 75 %
utilisation on a 1-year term. What breaks first is the token budget, then the billing mainframe; Cloud Run is
about 0.1 % of the bill.
