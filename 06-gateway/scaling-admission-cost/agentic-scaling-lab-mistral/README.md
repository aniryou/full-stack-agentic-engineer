# agentic-scaling-lab-mistral

The core concepts of scaling an agentic solution on Mistral models — as a primer, a cloud-neutral Kubernetes
reference architecture, and about 900 lines of runnable Python with four practice notebooks. Built for the
questions any deployment of it has to answer:
*how do we size this, what does it cost on Mistral's API and on our own GPUs, which of the two may we use, and
what breaks first.* Worked on one anchor scenario: a Singapore telco's support agent at 100,000 conversations a
day, with a residency requirement, on Mistral's API or on vLLM replicas in your own cluster.

Nothing here needs cloud credentials or a GPU; simulations run 50× faster than real time.

## The core concepts (`scalelab/`)

| Module | The idea |
|---|---|
| `capacity.py` | conversations → turns → calls → tokens/min; Little's law; the rate-limit request; cost per conversation on the API; the fleet sized for peak; the break-even GPU price; what breaks first |
| `serving.py` | what one vLLM replica delivers: KV bytes per token (GQA vs MLA) → resident sequences; HBM bandwidth → time per token; batch ↔ throughput; TTFT from prefill FLOPs (first-principles estimates to replace with `vllm bench serve`) |
| `model.py` | a fake Mistral model on three backends — the API (a shared TPM/RPS limit that answers 429), a fleet of replicas (that queue and slow down instead), and the hybrid (fleet first, API as spill-over) — plus the real calls: `mistralai` SDK and vLLM's OpenAI-compatible endpoint |
| `resilience.py` | token bucket (smooth your own traffic), backoff with full jitter, circuit breaker, `call_with_retries` bounded by a deadline |
| `admission.py` | degrade levels 0–3 from in-flight turns, pushback ratio (429/503), queue age and backend saturation; an in-flight cap; shedding with `Retry-After`; hysteresis |
| `loop.py` | the turn: budgets on four dimensions, a checkpoint per step, idempotent writes, resume after a crash |
| `tools.py` | simulated CRM / billing systems with QPS ceilings and structured errors |
| `sim.py` | a load generator: many users against any backend; latency, shedding, spill-over share and cost per regime |
| `clock.py` | the virtual clock |

## Quick start

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"             # its own venv: see the note below
python -m scalelab.capacity        # the capacity plan, both ways of paying
python -m scalelab.serving         # one replica per model and GPU
pytest -q                          # 19 tests, ~8 s
jupyter lab notebooks/             # start with 01_scaling_math.ipynb
```

To call the real things, `pip install -e ".[mistral]"`, set `MISTRAL_API_KEY`, and see `mistral_generate` and
`vllm_generate` at the bottom of `scalelab/model.py`.

This lab and `agentic-scaling-lab` both install a package named `scalelab`, so they cannot be installed side by side
in one environment: install one at a time (a venv each), or skip the install and run from the lab folder with
`PYTHONPATH=. pytest -q`. Renaming one package waits on a decision about folding the Mistral variants into the main lab.

## The notebooks

| # | Notebook | You will be able to |
|---|---|---|
| 01 | Scaling math — the API or your own GPUs | go from conversations/day to tokens/min, the rate-limit request, a replica's batch and latency, the fleet, dollars and the break-even GPU price in two minutes |
| 02 | The turn: budgets, checkpoints, idempotency | make a pod dying mid-turn produce one ticket, not two; know what to ack and what to nack on RabbitMQ |
| 03 | Rate limits, retries, breakers, admission | explain a 429 and the fleet that never sends one; smooth traffic; jitter retries; break circuits; degrade before shedding; write the spill-over rule |
| 04 | From a load test to Kubernetes and vLLM settings | show both forms of the overload loop and derive replicas, `--max-num-seqs`, the queue cap, the in-flight cap and KEDA thresholds from measurements |

Each notebook opens with the one-minute version, works the example against the code with charts, then hands
you four fill-in-the-blank exercises with checks. Practice notebooks run end to end untouched (checks print "not
attempted yet"); solutions run with every check passing.

These notebooks use their own check helper (`notebooks/nbutil.py`): an exercise is a `todo()` placeholder rather than
`# YOUR CODE HERE`, and a check prints `PASS`, `FAIL` or `---- not attempted yet` rather than the ✅ the root README
describes. An untouched practice notebook therefore shows no ✅ and no failure, by design.

## The anchor numbers (verify before quoting — prices, limits and GPU rates move)

100 k conversations/day → 15 model calls/s average, 46 at peak, 153 in an incident → 4.9 / 14.3 / 47.7 M tokens
per minute → a rate-limit request of 60 RPS and 19 M TPM (209 B tokens/month) → 42 / 125 / 417 turns in flight on the
API → $0.0131 per conversation on the planning mix (90 % Small 4 + 10 % Medium 3.5, prefix cached; $39.7 k/month) →
or a fleet of Ministral 3 14B on H100s: batch 24 at 20 ms per token, 1,200 tokens/s per replica, 4 / 11 / 34 replicas,
$55 k/month on on-demand GPUs, a 10 s turn instead of 6 → the fleet beats the API whenever an H100-hour costs less
than about $4.95 — so residency decides the path, and the arithmetic prices the decision. What breaks first is the
API limit or the peak-sized fleet at the incident, then the billing mainframe; Kubernetes is about 1 % of the bill.
